# 1.0 readiness

A standing assessment of whether Parley should cut `1.0.0`, what that would and would not promise,
and how to do it. **Nothing here cuts a release.** Per [`CLAUDE.md`](../CLAUDE.md), pre-1.0 breaking
changes land as `feat:`; 1.0 is cut deliberately, by a human, or not at all.

Last updated 2026-07-29, against `v0.9.0`.

---

## The case for 1.0

The version number should describe how stable the contract is. Parley's central contract is the
seam, and the seam has been frozen since v0.1.

**The seam has not moved in ten backends.** `packages/bridge-core/src/seam.ts` and `message.ts`
have been touched four times in the repo's history: once to define them, once for an npm scope
rename, once by the 71-finding audit (which changed wording, not shape), and once to add
`block_ms` — a single *optional* field. Every backend after SQLite landed with a `git diff` against
`bridge-core` that was empty. That is the design's whole bet, and it has now been tested ten times.

**It held for a capability invented after the freeze.** `block_ms` is the strongest evidence,
because it was not anticipated when the seam was designed. Adding server-side long-poll across nine
event-driven backends plus a generic fallback for polling-only SQLite required one optional field
and taught core no backend's name. A seam that only survives the backends it was designed around
has not been tested; this one absorbed a new capability.

**Six methods, one suite, ten implementations.** `connect · disconnect · subscribe · post ·
fetchRecent · resolveIdentity`. The shared conformance suite is written once against the interface
and runs against every plugin — the same eight cases, eleven times.

**The gate for splitting plugins into separate repos is met several times over.** `TASKS.md` set
that gate as "two consecutive backends land with zero core changes." Nine have. (We are choosing
not to split; that the condition is satisfied is the point.)

## What 1.0 would promise

- **The seam is stable.** A backend written against 1.0's `BackendPlugin` keeps working across the
  1.x line. New capabilities arrive as optional fields, as `block_ms` did.
- **The `Message` shape is stable** — `backendMsgId` and `cursor` semantics in particular: ordering
  and dedup come from the cursor and the id, never from timestamps.
- **The four MCP tools are stable** in name and argument shape.
- **Config keys do not disappear without a major.**

## What 1.0 would *not* promise

- **Tier-2 live `<channel>` push stays a research preview.** It rides Anthropic's `claude/channel`
  capability and can break on any Claude Code release. It has been verified only headlessly, via an
  in-process transport harness — **never demonstrated in a real interactive session**. That is the
  one open item in [`PROGRESS.md`](../PROGRESS.md) and it needs a human. The durable catch-up path
  (Tier 1) is the product and stands alone.
- **Vendor-hosted backends inherit their vendors' guarantees.** Discord, Slack and Telegram are
  SaaS: durability, identity and retention are under vendor policy, not ours.
- **Telegram cannot backfill.** The Bot API has no history endpoint, so `fetchRecent` replays a
  local store of messages this bridge observed. No pre-join history, ever. This is a documented
  fit-contract gap, not a bug to be fixed later.
- **`resolveIdentity` stays best-effort.** Most backends use a string convention; only Zulip hits a
  real directory endpoint.

## Verification matrix

What "verified" means per backend, stated so "ten backends" never reads as "ten live-tested
backends."

| Backend | Verified against | In CI |
|---|---|---|
| SQLite | a real on-disk file, incl. forked multi-process writers | yes |
| Redis | real `redis:7` | yes |
| NATS | real `nats:2.10` JetStream | yes |
| Postgres | real `postgres:16` (`LISTEN`/`NOTIFY`, advisory-lock-ordered `BIGSERIAL`) | yes |
| Matrix | live Synapse homeserver | yes |
| XMPP | live Prosody with MAM | yes |
| Zulip | in-process API fake; **plus** an env-gated real-server suite and maintainer operation | fake only |
| Discord | in-process fake of the gateway + REST | fake only |
| Slack | in-process fake of Socket Mode + Web API | fake only |
| Telegram | in-process fake of the Bot API | fake only |

Also in CI: the external-OIDC path against a real Keycloak 26.3 realm.

**CI now fails if any test file skips itself.** This matters more than the row count: before that
gate, seven of 57 files self-skipped on every green build — including the conformance suites for
the two largest plugins — and the summary line looked identical to a real pass. Current state: 460
tests across 58 files, none skipped.

### The honest gaps

- Four backends have never been run against a live vendor account in an automated way. Their fakes
  encode our *understanding* of each API, so a mismatch between fake and reality is invisible. This
  is not hypothetical: Matrix's `block_ms` passed every fake and every adversarial review, and only
  a real homeserver caught it returning in 37 ms when asked to wait 300.
- Tier-2 live push has no automated real-session coverage at all.

## How to cut it, when you decide to

The bump comes from the squash-merge subject, so a PR titled with a `!` or carrying a
`BREAKING CHANGE:` footer publishes `1.0.0` across all 13 packages the moment it merges. Either:

1. **Deliberate conventional commit** — a PR whose title carries `feat!:` (or a `BREAKING CHANGE:`
   footer), merged to `main`. `semantic-release` tags `v1.0.0`, cuts the GitHub Release, and
   publishes every package in lockstep with provenance.
2. **Manual dispatch** — run the *Publish (manual)* workflow with `1.0.0`. This is the escape hatch;
   prefer path 1 so the tag and the release notes stay in step.

Before either, confirm `main` is green *and* that the run actually executed the backends rather than
skipping them — the skip gate makes that automatic now, but read the log anyway.

## What would change this assessment

- A backend that cannot be expressed through the seam without a core change. None has appeared in
  ten, but the population is self-selected: every backend so far was chosen partly because it
  looked like it would fit. A queue-only transport with no history, or one with no stable per-message
  id, would be the real test.
- Live-vendor verification for the four fake-only backends turning up a fake-vs-reality mismatch.
- A real interactive-session demonstration of Tier-2 push either working or proving unworkable —
  which would move it out of "preview" in one direction or the other.
